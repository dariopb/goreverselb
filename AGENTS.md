# AGENTS.md

## Scope

This repository is a Go 1.24 L4 reverse-tunnel/load-balancer. The production executable is `./cmd/goreverselb`; `./cmd/main.go` is a separate hard-coded development harness and is not the normal CLI entry point.

No repository-specific Cursor, Copilot, Claude, or prior agent instructions are present.

## Essential commands

Run commands from the repository root unless noted otherwise.

```bash
# Build the production CLI (writes ./goreverselb by default)
go build ./cmd/goreverselb

# Build the static Linux binary used by the Docker files
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -ldflags="-s -w" -v ./cmd/goreverselb

# Compile every package while bypassing the repository's existing vet failures
go test -vet=off ./...

# Run normal tests plus vet once the existing vet findings are relevant/fixed
go test ./...
go vet ./...

# Format hand-written Go files that were changed
gofmt -w <files>

# Regenerate embedded REST assets after changing pkg/restapi/web/*
go generate ./pkg/restapi
```

There are currently no `*_test.go` files. `go test -vet=off ./...` is therefore primarily a whole-repository compile check. Plain `go test ./...` currently fails because Go's vet phase reports pre-existing printf-format issues in `cmd/main.go`, `pkg/muxtunnelClient.go`, `pkg/pool.go`, and `pkg/pubsub/lruslogger.go`. Do not interpret that known failure as a compiler failure; `go build ./cmd/goreverselb` and `go test -vet=off ./...` pass.

`pkg/restapi/statik/statik.go` is generated by Statik and is the only tracked Go file not currently `gofmt`-clean. Do not hand-edit or reformat it. The generator directive expects the `statik` executable at `$GOPATH/bin/statik`.

The Docker recipes assume the Linux binary already exists at repository root:

```bash
docker build -f docker/Dockerfile-alpine.txt -t <image> .
docker build -f docker/Dockerfile-alpine-tunnelgroup.txt -t <image> .
```

`docker/Dockerfile` is different: it copies `cmd/goreverselb` as though that path were already a binary, while the current tree uses it as a source directory. Prefer the Alpine recipes unless deliberately repairing that file.

## Running the CLI

The global token flag is required and must precede the subcommand:

```bash
go run ./cmd/goreverselb -t 1234 server -p 9999 -s localhost
go run ./cmd/goreverselb -t 1234 tunnel -e localhost:9999 -s example -b 127.0.0.1:8080
go run ./cmd/goreverselb -t 1234 tunnelgroup -e localhost:9999 -g '<service-group-json>'
```

CLI environment variables use the `REVLB_` prefix, for example `REVLB_TOKEN`, `REVLB_PORT`, `REVLB_API_ENDPOINT`, `REVLB_SERVICE_ENDPOINT`, and `REVLB_SERVICE_GROUP_JSON`. Some historical examples in `.vscode/launch.json` and `docker/generateDocker.txt` use older unprefixed or `LB_` names; those do not match the current `urfave/cli` flag declarations in `cmd/goreverselb/server.go`.

The server creates or updates these files relative to its process working directory:

- `user_store.yaml`: persistent user/token configuration. Startup always sets the default user's token to the current global token and saves the file.
- `revlb_ssh_host_key`: persistent Ed25519 host key for SSH-wrapped frontends, created with mode `0600` if absent.

Treat both as runtime state. Root-level copies and built executables are intentionally untracked in some working trees; do not include them in source changes or expose their contents.

## Code organization

- `cmd/goreverselb/`: production `urfave/cli/v2` application. `server.go` contains both CLI registration and server startup; `client.go`, `servicegroup.go`, and `stdinProxy.go` implement subcommands. All flags write into the package-global `cfg` from `config.go`.
- `cmd/main.go`: standalone experimental/demo program with hard-coded ports, hosts, users, and long sleeps. It is included by `go test ./...`, but not by production builds of `./cmd/goreverselb`.
- `pkg/muxtunnel.go`: server-side TLS listener, yamux session registration, dynamic frontend listeners, instance selection, SSH/TLS frontend wrapping, and bidirectional proxying.
- `pkg/muxtunnelClient.go`: reconnecting tunnel client. It registers tunnel metadata on a control stream, accepts yamux streams for incoming frontend connections, dials a backend target, and proxies both directions.
- `pkg/muxtunnelClientServiceGroup.go`: reconciles declarative service-group JSON into a set of `MuxTunnelClient` instances, keyed by service and `protocol-port`.
- `pkg/types.go`: shared wire/config models and the small length-prefixed stream frame protocol.
- `pkg/pool.go`: synchronized allocation of the configured dynamic frontend port range.
- `pkg/restapi/`: optional Echo status API and embedded static web UI. The API is plain HTTP despite receiving a TLS certificate argument.
- `pkg/pubsub/`: optional in-process NATS Streaming server.
- `pkg/helpers/`: YAML/JSON persistence chosen solely by filename extension.
- `pkg/certHelper/`: creates a fresh self-signed RSA certificate at every server start.
- `version/`: build-visible version string, currently defaulting to `latest`.
- `docker/`: historical image/deployment recipes; `docker/generateDocker.txt` is a command log, not an automated build script.

## Control and data flow

1. `server` loads `user_store.yaml`, overwrites the default user's token from the CLI, creates a new self-signed TLS certificate, and starts `MuxTunnelService`. Optional REST and NATS listeners start only when their ports are nonzero.
2. A `tunnel` client converts `serviceendpoint` into target host/port and encodes an instance as `serviceName:instanceName`. It maintains one or more outbound TLS connections to the server and wraps each in yamux.
3. The first yamux stream is the long-lived control stream. The client JSON-encodes `TunnelData`; the server parses user/service/instance context, authorizes it, allocates or reuses a frontend port, registers the yamux session, and returns `TunnelDataResponse`.
4. Each public frontend connection causes the server to choose an instance and a random registered yamux session, open a new yamux stream, send a two-byte little-endian length plus JSON `TunnelConnecData`, then copy bytes in both directions.
5. The client reads that frame, randomly chooses one of its target addresses, dials `target:port`, and proxies the stream. Both proxy sides preserve TCP half-close behavior via `CloseWrite`/`CloseRead` when the connection supports it.
6. When the last backend session for a service disappears, the server closes that service's frontend listener and returns its port to the pool.

### Instance routing

The maps are nested as user -> service -> instance -> backend session. Delimiters are part of the wire convention:

- `TunnelData.ServiceName`: `service:instance`
- `TunnelData.Token`: a token containing `:` causes the prefix to be treated as the user ID

Avoid introducing `:` into service names, instance names, or ordinary default-user tokens without reviewing `parseServiceContext`, which uses unrestricted `strings.Split` and only the first two fields.

If a frontend is not already associated with an instance, the server reads up to the first 1024 bytes, with a 50-second deadline, and tries in order:

1. TLS ClientHello SNI
2. Custom `PROXY->` preamble: seven ASCII bytes, one byte of instance-name length, then the instance bytes
3. HTTP `CONNECT ` target

The first bytes are replayed to the backend except for the consumed custom preamble or HTTP CONNECT request. A connection that supplies none of these routes to the empty instance name, so a matching empty-instance registration must exist.

`stdinproxy` emits the custom preamble for non-TLS connections. With TLS wrapping it sets SNI to `--instancename`, or to the endpoint string when no instance is supplied.

## Conventions and change patterns

- Use standard Go formatting and import grouping. Existing source commonly aliases the root `pkg` package as `tunnel` and Logrus as `log`.
- Shared externally serialized fields live in `pkg/types.go` or the service-group models and carry explicit JSON tags; persisted user/tunnel models generally carry matching YAML and JSON tags. Preserve field names and framing for wire compatibility.
- Runtime maps and mutable tunnel fields are protected by explicit mutexes. Keep lock scopes consistent, and never perform long network copies while holding a service/client mutex.
- Network listeners and sessions run in goroutines. Shutdown is channel-driven, while reconnecting clients retry after `addBackendConnection` returns. Changes to close behavior must account for repeated closes and blocked goroutines.
- Frontend port `0` means allocate from `[dynport, dynport+dynportcount)`. Explicit ports must also belong to that pool; the allocator does not permit arbitrary ports outside it.
- Multiple registrations with the same user/service/instance are load-balanced randomly at the yamux-session level. Service-group clients additionally load-balance randomly across `BackendIPs` locally.
- Preserve half-closes in proxy code. Replacing the two-direction copy with a single full `Close` can truncate request/response protocols; this behavior was an intentional prior fix.
- Update `README.md` when changing CLI flags, environment variables, service-group JSON fields, or user-visible tunnel behavior. Update and regenerate `pkg/restapi/statik/statik.go` when changing web assets.

## Testing changes

Because there is no existing automated test suite, add focused `*_test.go` files for deterministic units when changing parsing, framing, allocation, reconciliation, or authorization. Prefer loopback listeners and generated in-memory configuration for network tests; constructors start goroutines and may create working-directory state.

After each Go change, run at least:

```bash
gofmt -w <changed-go-files>
go test -vet=off ./...
go build ./cmd/goreverselb
```

Run `go vet ./...` too and distinguish newly introduced findings from the known printf findings listed above. For protocol or lifecycle changes, exercise an end-to-end local server/client pair because compilation cannot validate yamux stream ordering, instance dispatch, port reuse, or half-close semantics.

## Security and operational gotchas

- The tunnel transport currently creates a fresh self-signed server certificate, and `NewMuxTunnelClient` unconditionally sets `InsecureSkipVerify = true`. The tunnel command's `--insecuretls` value is not passed into that client. Do not claim certificate verification exists without changing this path end to end.
- SSH-wrapped frontends currently accept every username/password. The destination requested by SSH `direct-tcpip` is used only to construct address metadata; traffic is still sent through the registered reverse tunnel backend.
- `AllowedSources` is persisted but source-range enforcement in `doProxy` is commented out.
- The REST listener is unauthenticated plain HTTP and exposes only the default user's service map. Its `token` and certificate parameters are currently unused.
- Avoid logging tokens or dumping `TunnelData` in new code. Existing client logs include the full tunnel struct, including its token; do not copy that pattern.
- The custom frame length is a `uint16`, while `readFrame` rejects payloads over 1000 bytes and assumes each `Read` returns the entire requested segment. Any framing change must be coordinated on both client and server.
- Dynamic certificates are regenerated on every start; only the SSH host key persists.
